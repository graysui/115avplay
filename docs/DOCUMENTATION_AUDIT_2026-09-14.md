# MediaVault 全项目文档与实施计划审核

审核日期：2026-09-14。审核对象为当前工作区的全部 16 份 Markdown 需求、设计、参考规范和计划；现有 Python、SQL 及提取文本仅用来理解资产与验证依据，不进行代码质量审核。本报告是审核意见，不替代原需求，也不表示建议方案已获采纳。

## 1. 结论

**项目方向可行，但当前文档尚不足以直接按计划实施并满足全部验收承诺。** Go 单进程、SQLite、数据库投影媒体库、115 就绪资源直连，以及前端嵌入二进制的组合没有明显架构障碍。主要问题集中在旧库升级、外部协议证据和运行时资源生命周期，而不是语言或框架选型。

共记录 **22 项问题：3 项阻断、14 项高优先级、5 项中优先级**。这里的级别表示修订紧迫程度，与实施阶段 P0～P8 的编号无关。

- **阻断**：旧库迁移不能达到目标结构和状态；115 关键链路缺少完整可执行契约；占位短片不能证明第三方客户端可以自动恢复播放。
- **高优先级**：错误降级、多版本转存、任务恢复、安全清理、可播性、评分、刮削、身份归一化、摄取、扫描、协议、进度、权限与就绪探针，均存在会改变实现结果的缺口。
- **中优先级**：关键路径计算、性能验收条件、需求到任务的覆盖、分类语义、文档细节需要统一。

建议先修订阻断项并完成最小播放验证，再冻结数据契约和生命周期规则，随后执行原阶段计划。**不建议把现有 27～37 人日估算当作已验证的交付承诺。**

## 2. 项目理解与审核依据

项目的主链路是：本地全量离线库作为初始目录，AVDB 30D 包及 JavDB 榜单/搜索持续补充影片和资源；刮削补全展示信息并选出默认版本；Emby 适配层投影分类、详情和用户进度；115 永久库优先供片，缺失时执行临时离线下载；客户端通过 302 访问就绪视频；Janitor 到期回收临时资产。

这条链路有四类不同的状态，实施时必须分别明确：影片元数据、逻辑资源身份、115 物理资产、异步任务及播放会话。目前后两类状态主要挤在 `offline_magnets` 的单行中，是多个问题的共同来源。

文档层级已有合理基础：`spec.md` 定义需求，主设计定义技术细节，`plan.md` 与九个阶段文件组织实施。`MEDIA_LIBRARY_SPEC.md` 已明确标注历史参考和概念草案，因此其中 PostgreSQL、多网盘、电视剧和转码等内容，**不作为现行设计自相矛盾的证据**。

## 3. 阻断项

### A01 — 旧库迁移计划无法实现目标 Schema 和业务状态

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §4.1～§4.4，尤其第 163、184、190、327～330 行；[数据层计划](../specs/mediavault-server/phases/01-data-layer.md) T-107、验收 2/4；[需求](../specs/mediavault-server/spec.md) NFR-6。

计划只明确补充时间列和辅助表，并要求不重建表。但旧库没有 `resource_kind`；`offline_magnets` 的外键不是级联删除，`source_type` 也没有新设计的 CHECK，旧列默认值与新定义不同。`CREATE TABLE IF NOT EXISTS` 不会更新现有表，单纯增加列也不会改变旧外键和已有列约束。由此，空库与升级库会有不同语义，P1 的级联删除验收不能同时成立。

数据状态也不能原样继承：旧库全部 326,808 条资源没有 pick_code，却都标为可播；18,239 部“完整成功”影片没有简介，按新规则应属于部分成功。仅补列后启动，会误报可播数量并让这些影片永远跳过补全。

补时间列还存在 SQLite 实施限制：对含数据表增加 `DEFAULT CURRENT_TIMESTAMP` 会报 `Cannot add a column with non-constant default`；`ADD COLUMN IF NOT EXISTS` 也不是该 SQLite 的合法语法。文档中的幂等原则需要落实为版本判断和列检查，不能统一套 SQL 关键字。

**建议**：增加逐列、逐约束、逐状态的旧库差异表。推荐允许“备份后、事务内受控重建表并完整搬运数据”，明确它不是删除业务数据；若坚持不重建，则需修改目标约束和验收。补充时间值来源、资源类型回填、可播性重算、旧刮削状态转换、索引创建前检查以及失败恢复策略。区分事务回滚、备份恢复、旧版本程序重新启动三种含义。

**关闭条件**：在旧库副本上升级后，主键集合和业务数据保留，新增约束与空库一致；无 pick_code 的资源不可播；缺简介的旧成功记录按新规则转换；中断后重启可恢复；重复迁移无变化。对外键级联和回滚方案分别验收。

### A02 — 115 核心链路的参考资料不足以形成可实施契约

**依据**：[115 客户端计划](../specs/mediavault-server/phases/02-115-client.md) 第 9、18～26 行；[字段参考](../references/115_openapi_field_spec.md) Part A §9、Part B；[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §5.4、§8；[115 提取文本](../references/mediavault_115_client_reference.txt)。

字段参考主要覆盖文件接口，云下载详细样例属于 Cookie 协议。当前 OpenAPI 方案只给出了 `add_task_bt`、`add_task_urls`、`downurl` 等名称或路径，缺少完整请求、原始响应和业务错误分类。提取文本是符号/字符串集合，不等于完整 SDK 或已验证请求契约。初次授权、授权应用条件、scope、刷新令牌轮换、离线任务身份、完成后目录/文件定位、额度和删除完成语义均没有串成一条完整流程。

这不证明接口不可用，而是意味着 T-206 不能仅凭现有文档确定“磁力如何变成可 Range 播放的文件”。“115 是唯一未验证外部链路”也不能作为排期依据：JavDB 逆向参考和旧客户端交互记录，同样不能证明新服务当前可端到端运行。

**建议**：在大规模实现前增加最小验证阶段，补齐“取得授权 → 列目录 → btih/ed2k 分别添加 → 查询状态 → 定位结果 → 取链 → 客户端 Range → 受控清理”的脱敏请求/响应、日期与条件。明确 302 链接对 UA、客户端 IP、附加下载头、有效期的要求，以及代理对这条链路的影响。用这些事实决定缓存键和支持范围。JavDB 另需固定搜索、详情、磁力、评论的字段映射和可复现样例。

**关闭条件**：最小链路在新项目使用的授权方式下验证成功；mock 契约测试引用同一批样例；未验证能力标为待定，不能写成必然可用。

### A03 — 占位短片不能保证第三方客户端自动恢复播放

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §8.4 第 633～635 行；[播放计划](../specs/mediavault-server/phases/05-playback-115.md) T-506、验收 2；[需求](../specs/mediavault-server/spec.md) US-3、FR-STREAM-4、AC-6。

方案在等待 8 秒后 302 到约 5 秒的 MP4，并期待 Infuse/VidHub 显示“准备中”及重试。普通播放器没有理由识别自定义 `X-MV-Preparing`，尤其该头附在重定向响应上；MP4 文件也不会自行要求播放器循环或重新请求原地址。客户端可能正常播放短片、结束播放，甚至将这段进度或完播状态记到正片。等待超时后的用户体验因此没有被协议闭合。

**建议**：把“资源已就绪的秒播”和“冷资源准备”拆成两种明确交互。推荐首版采用后台预准备或明确的用户手动重试流程；若坚持占位流，必须逐客户端证明提示、重试和进度隔离，不能假设自定义响应头被支持。

**关闭条件**：对每个承诺支持的客户端，转存超过等待时间时，记录实际界面、是否发起重试、最终取得的版本、是否污染正片进度。只有实测通过的行为才能进入 AC-6。

## 4. 高优先级问题

### A04 — 取链错误被当成文件不存在，且永久库失效后的转存回退不完整

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §7.3、§8.3 第 621 行、§8.4 第 629～636 行；[扫描清理规范](../references/115_tree_scan_and_cleanup_spec.md) 第 222 行。

`errno≠0` 就清 pick_code 会把令牌失效、限流、超时等暂时故障误判为资源消失，引发无谓重扫或再次转存。另一方面，`existing` 失效只安排目录重扫，没有定义重扫找不到后如何改选 btih/ed2k；所有资源失效时又保留最高分 preferred，可能继续选中不可转存的 `existing`，反复重扫。

**建议**：定义 `not_found/auth/rate_limited/transient/unsupported` 错误分类，仅确认不存在时解绑文件。失效后先遍历其他可播版本，再挑选可转存类型；对没有候选的情况给出终态。只有客户端确实访问成功才能证明无死链，服务端一次 downurl 成功不能保证后续 CDN 请求永远有效。

**验收**：分别注入令牌过期、429、超时、文件删除和无候选；前几类保留资源绑定，文件删除能切换到真实可用候选，不能形成重扫循环。

### A05 — 按番号单飞与多版本选择冲突

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §8.4 第 627、632、636 行、§9 第 645 行；[需求](../specs/mediavault-server/spec.md) US-4、FR-STREAM-6。

两个客户端同时为同一影片选择 1080P 和 4K 时，`movie_code` 级单飞只保留一个任务，但这两个请求并不是同一资源。后一个请求可能拿错版本，或一直等待自己所选资源变为就绪。

**建议**：推荐以“115 账号/绑定 + 资源身份”作为转存幂等键；番号级锁只用于短事务内的 preferred 重选。显式指定 `MediaSourceId` 时优先保证版本语义，失败后能否自动换版需另行规定。

**验收**：同影片同版本并发只建一个任务；不同版本请求不串流；`MediaSourceId` 不属于该影片时拒绝。

### A06 — 异步任务缺少持久化身份和中断恢复契约

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §4、§8.4、§11 `job_registry.go`；[摄取计划](../specs/mediavault-server/phases/03-ingestion.md) T-308；[后台计划](../specs/mediavault-server/phases/07-admin-console.md) T-707。

计划要求转存轮询、同步 run 审计、任务进度和长期无人值守，但九表 Schema 没有任务/run 的明确定义，也未规定它们怎样持久化。`transfer_status=1` 无法说明对应哪个远端任务、何时开始、何时超时、重启后谁接管。若远端已接收任务而本地尚未记录成功便崩溃，内存 single-flight 不能避免重复提交；反过来也可能永远卡在“转存中”。

**建议**：在设计层选定任务表或等价持久化记录，至少包含任务类型、资源/远端身份、状态、尝试次数、重试时间、执行租约、结果目录、错误和开始/完成时间。规定提交结果未知时先对账、再决定是否重发；给转存、刮削、同步分别设置超时和恢复规则。九表数量应随设计调整，不能反过来限制必需状态。

**验收**：覆盖远端接收后崩溃、回填前崩溃、轮询中重启、任务永久失败及重复手动触发；恢复后任务可追踪且不会无限等待。

### A07 — 清理缺少资产所有权、删除确认与并发保护

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §4.2、§8.2、§10.1 删除影片；[扫描清理规范](../references/115_tree_scan_and_cleanup_spec.md) §3～§5；[播放计划](../specs/mediavault-server/phases/05-playback-115.md) T-504。

“位于临时根目录之下”只是删除范围，不是资产归属证明。永久库与临时根重叠、文件被移动、配置修改、正在播放或重新转存时，现有规则没有明确保护。Schema 只保存主视频 ID 和存放目录，未明确保存任务创建的独占目录及其余文件；因此“零垃圾残留”缺少可实现依据。

文档知道删除是异步的，却仍缺少确认未完成时的状态和重试约定；固定等待 1～2 秒不是完成证明。若直接清空本地绑定，后续可能丢失清理目标。管理端级联删除影片也会抹去这些目标，留下云端临时文件。

**建议**：记录任务拥有的文件/目录，拒绝删除配置根本身和永久资产；验证两个根的相互包含关系；删除前重新核验归属与有效播放租约。使用“待删 → 已提交 → 已确认”的持久状态，在确认之前保留目标身份。影片删除需先安排资产清理，或保留独立清理记录。另需实测普通删除、进入回收站和释放额度的区别，不能默认一次 delete 即释放全部空间。

**验收**：覆盖根目录重叠、外部移动、并发重转存、活跃播放、异步删除未完成、进程重启和删除影片；既不误删，也不遗忘未完成清理目标。

### A08 — 可播性依赖时间，但重算触发器仅覆盖写库

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) 第 183～185、589～606、618 行；[需求](../specs/mediavault-server/spec.md) §7；[播放计划](../specs/mediavault-server/phases/05-playback-115.md) T-501。

临时资源越过 `temp_expire_at` 时即使没有写库，也会从可播变为不可播。只在写库时重算不能保证索引字段与真实条件一致；Janitor 尚未运行或被关闭时，列表和 preferred 可能仍认为它可播。现有永久库写入契约没有设 `transfer_status=2`，§8.0 又允许它绕过该条件，与字段注释和 T-501 的摘要不同。清理状态在枚举中是 `3`，实际清理流程却写 `0`。

**建议**：统一状态转换表，明确 existing 的 ready 状态、NULL TTL 含义、清理后状态以及失败后的可重试性。所有选源查询和播放前校验包含实际时间条件；派生字段只能作为有时效限制的缓存。说明关闭清理时 TTL 是否仍影响可播性，以及修改 TTL 是否追溯已有资源。

**验收**：冻结时钟到过期前后，不触发其他写入且关闭 Janitor，选源和可播结果仍正确；各路径的清理状态一致。

### A09 — 优选算法与“永久库优先、严格权重”的说明不一致

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §7.2、§7.3、§8.3 第 618 行；[刮削计划](../specs/mediavault-server/phases/04-scraping.md) T-406/407。

文档函数让唯一资源得 999999，而永久库固定得 900000，却说明后者“高于任何磁力”。第一条资源入库后再新增版本时，也没有明确要求重算所有旧候选的 `hasOnlyOne` 相关分数，因此存在旧分数永久占优的实现分歧。若播放入口另行硬编码 Tier1 优先，preferred 和实际默认播放也可能不是同一版本。

关键词识别还有可复现反例：“无字幕 1080P”因含“字幕”得到 110400 分，高于普通 4K 的 25400；“有码”本身没有独立评分维度，1080P 被当成“标准有码”的替代指标。

**建议**：将 Tier、可播状态和质量偏好分开排序；唯一候选直接选中，不给它永久超高分。新增、修改、清理资源时重算受影响影片的全部候选。定义有边界且支持否定词的字幕/破解/分辨率标记，并明确“有码”是否真是独立偏好。

**验收**：包含唯一变多条、临时资源与永久资源共存、无字幕/软字幕、标题冲突、同分排序、人工修正后的重选样例。

### A10 — 刮削失败、部分成功和免刮削规则没有统一状态表

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) 第 142～145 行、§5.1、§6、§7.4；[需求](../specs/mediavault-server/spec.md) FR-SCRAPE-2/3；[刮削计划](../specs/mediavault-server/phases/04-scraping.md) T-404、验收 2。

规则存在三种口径：流程图按年龄放弃，代码示例要求超龄且 404、或任何失败达到三次，阶段验收则写超龄或三次仍失败。三次临时网络/风控故障可能把有效影片永久置 `2`。重试次数的列注释是累计，失败原因又称连续，成功后是否重置没有规定。

部分成功 `3` 可以永远重试，却没有下一次执行时间、最大补全预算或人工恢复规则；部分成功后网络失败在流程图中还会退回 `0`。`2` 同时表示 FC2/国产、2025 前老片和放弃，无法明确“包含失败”是否允许重新刮削。在线入库统一置 1/3，又与 FC2/国产免刮削口径不同。最后，`publish_date` 混用论坛发帖日与正式发行日，十天规则的含义会随来源变化。

**建议**：分开内容完整度、执行状态、跳过原因和重试资格；临时故障触发上游退避，不永久判定影片无数据。规定成功后的计数重置、部分成功补全间隔、手动恢复和日期来源，明确 2025 截止线是迁移历史规则还是长期规则。

**验收**：覆盖 404、429、超时、缺字段、NULL/未来日期、部分成功后失败、成功后再失败和管理员重试；每种情况的下一状态与下一执行时间唯一确定。

### A11 — 番号和资源唯一键的归一化契约不充分

**依据**：[扫描清理规范](../references/115_tree_scan_and_cleanup_spec.md) §2，第 79、97～125 行；[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §5.4、§7.4 第 563 行；[摄取计划](../specs/mediavault-server/phases/03-ingestion.md) T-303/305。

直接执行文档正则得到：`SSNI-999_CH_HD → 空`、`IPX123 → IPX1-23`、`H264-1080 IPX-123 → 空`。原因分别是下划线处的词边界、可吃数字的贪婪前缀，以及只检查首个候选后停止。这些是身份匹配规则本身的问题，会让扫描漏片或产生错误番号。

资源键又称“40 位十六进制”，但 `EXIST` 含非十六进制字符。btih 只定义 40 位格式，未明确 32 位 Base32 等输入的支持边界；ed2k 对整条链接做 SHA1，只清理空白/标点，同内容不同文件名或等价编码不会统一。全局 hash 唯一且资源只关联一个 `movie_code`，还需规定合集或同 hash 被不同番号认领时的处置。

**建议**：制定跨 CSV、在线搜索、目录扫描共用的规范化样例表；优先使用精确候选和分隔符规则，尝试后续候选。将资源 ID 定义为类型化不透明键，区分内容 hash 与资源主键，明确等价链接和多番号冲突策略。主设计 §7.4 的“按 §2 归一化”应指向扫描参考的准确章节。

**验收**：正文已有全部示例通过；补充紧凑番号、下划线、分辨率噪声、合法 Base32、ed2k 等价链接及跨番号 hash 冲突样本，结果固定。

### A12 — 增量摄取缺少中断补齐和跨源更新规则

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §5.1、§5.2 第 385 行、§7.4 第 574 行；[摄取计划](../specs/mediavault-server/phases/03-ingestion.md) T-306～308；[刮削计划](../specs/mediavault-server/phases/04-scraping.md) T-409。

每日只取最新 30D 包，停机超过窗口时无法恢复中间缺口；当前没有首次全量导入、漏期追补或全量对账的服务端流程。只靠资源主键去重，也不能回答同一 release 两个包部分成功后如何重试、上游修正同 hash 信息如何更新、何时写成功水位。

“重复 hash 自动忽略”与“upsert 仅补空字段”口径不同；“仅补空字段”若被普遍采用，会让先入库的低质量信息和非空默认值阻止后续修正。榜单流程还写了已有番号的磁力核对，但 T-409 只安排未收录番号。影片表在没有磁力时就存在，也会让后续按“影片存在”判断跳过补资源。

**建议**：定义 release/asset 身份、校验值、分包进度和成功水位；明确超过 30 天的恢复办法。增加逐字段来源优先级及空值定义，将运行时绑定与外部元数据更新隔离。榜单对账根据影片与资源完整度分别决策，而不只判断影片是否存在。FC2/国产免刮削规则必须优先于“新影片统一置 0”。

**验收**：停机 45 天、同批次半途失败、一个包失败、重复包字段更新、先在线后离线、只有影片无资源等场景均有明确结果。

### A13 — 扫描范围和删除对账无法由当前步骤完整实现

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §8.3；[115 字段参考](../references/115_openapi_field_spec.md) 第 428～446 行；[115 客户端计划](../specs/mediavault-server/phases/02-115-client.md) T-204；[扫描清理规范](../references/115_tree_scan_and_cleanup_spec.md) §1。

主流程只列根下目录、从目录名提号，再找最大视频，没有明确根目录散放视频、多层分类目录、同影片多个版本目录及未识别目录继续下钻的规则。参考明示 `type=4` 包含 ISO，而需求排除原盘直读；仅选最大文件可能选中不支持的 ISO 或丢掉分段正片。

同步没有定义完整扫描标记和失败隔离。分页失败或限流时，“这一轮没看到”不能等于“文件已删除”。按 `upt` 增量也会漏移动进来的旧文件；参考已经指出移动不改 upt，数量相同的一进一出更不能靠 count 完整发现。

**建议**：明确首版支持的目录形态、容器和多文件影片边界；全量扫描与增量分开。仅在一个根的完整快照成功后淘汰缺失绑定，记录扫描代次/最后看到时间，并安排周期性全量对账。先通过实际支持格式过滤，再执行最大视频策略。

**验收**：嵌套目录、散放文件、ISO、大正片加 sample、分段视频、第二页失败、同数量文件移动等样例都有确定处理方式。

### A14 — Emby 最小协议尚不足以支持“完整无感接入”的承诺

**依据**：[Emby 接口参考](../references/emby_protocol_endpoints.md) §1～§4；[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §9；[Emby 阶段计划](../specs/mediavault-server/phases/06-emby-protocol.md) T-601～613；[路由提取文本](../references/mediavault_emby_router_reference.txt)。

现有清单有列表/详情/流，但没有冻结 PlaybackInfo 协商、用户 views、会话能力、路由大小写/可选前缀、完整鉴权头格式、HEAD/Range、稳定 ItemId/ServerId 生成和 URL 基址规则。参考提取文本出现 `playbackinfo`、`views` 等符号，只能说明这些步骤值得核实，不能作为“已兼容”的证明。列表参考还规定 `SortOrder`，T-606 的参数清单没有它。

仅下发 `MediaSources` 也没有约定 Path/DirectStreamUrl、MediaStreams、实际容器、版本选择和就绪状态怎样关联。直接写 `SupportsDirectPlay/DirectStream=true` 不证明客户端支持该视频。需求排除转码，却承诺较广客户端范围；其中浏览器或 Emby Web 的播放能力需要单独限定。

**建议**：把目标收敛为带版本号的客户端矩阵，先捕获“登录 → 分类 → 详情 → 协商 → 播放 → 续播”请求链，再冻结对应最小接口。未支持的转码/封装请求应有明确能力声明和结果。稳定 ID、鉴权、分页排序和反向代理地址是该契约的一部分。

**验收**：契约样例可重放，两款目标客户端实际流程通过；Kodi/浏览器等未验证对象不自动继承通过结论。

### A15 — 时长来源、播放会话与进度幂等性没有闭合

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §4.1～§4.3、§9.4；[Emby 接口参考](../references/emby_protocol_endpoints.md) 第 109～110、185～198 行；[Emby 阶段计划](../specs/mediavault-server/phases/06-emby-protocol.md) T-611。

Movie DTO 要求 `RunTimeTicks`，完播判断依赖 duration，但影片/资源表没有明确时长来源与映射，客户端上报样例也不带 duration。评分源是 0～5，参考 DTO 使用 8.5，亦缺少明确换算。`PlaySessionId` 的生成与返回时机没有定义。

停止上报每次满足 90% 就 `play_count+1`，客户端重复上报会重复计数；两设备交错心跳可能覆盖较新的进度。更新流程没有明确写 `last_played_at`，而继续观看正按该字段排序。占位短片与正片共用 ItemId 时问题会进一步扩大。

**建议**：定义时长、评分、容器等字段的来源、单位与未知值；不伪造无法获取的媒体信息。播放会话持久化完成状态，以一次会话的首次完播计数，定义迟到事件及多设备冲突策略；同时维护继续观看时间，并隔离准备阶段事件。

**验收**：未知时长不除零/误完播；重复 stopped 只计一次；旧设备迟到心跳不错误覆盖新会话；续播排序、不同版本时长和评分展示符合固定契约。

### A16 — 登录校验不能代替权限约束，配置加密也缺少启动契约

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §4.3、§9.3～§9.4、§10.1；[基础阶段](../specs/mediavault-server/phases/00-foundation.md) T-003；[后台阶段](../specs/mediavault-server/phases/07-admin-console.md) T-701/703；[需求](../specs/mediavault-server/spec.md) AC-9、NFR-7。

文档只明确命中 session 即通过、写入按 `(user_id,movie_code)` 隔离，但没有要求 URL/body 中的用户必须等于登录用户，也没有明确所有管理 API 检查 `is_admin`、已禁用用户和过期会话无效。复用同一会话表时，普通 Emby 用户不能因此获得配置/删除权限。

“敏感值加密”没有规定主密钥来源、丢失后恢复、令牌刷新原子持久化及配置优先级。管理端返回脱敏占位值后，整份配置 PUT 是否会用占位值覆盖真凭据也未定义。Cookie/Bearer 二选一未定，Cookie 模式的跨站请求与 WebSocket 会话校验应随之确定。

**建议**：补最小权限矩阵（公开、本人、管理员），集中验证 enabled、到期时间和资源归属；区分登录认证与操作授权。规定密钥启动配置、备份恢复、secret 的“保持/替换/清除”语义、日志脱敏与环境变量优先级。P0 在读取尚未由 P1 创建的设置表前，需明确默认配置和迁移的启动顺序。

**验收**：A 不能改 B 的进度，普通用户不能访问管理接口，停用/过期会话被拒绝；保存普通配置不破坏凭据；重启和密钥恢复后可解密；未授权 WS 无法订阅日志。

### A17 — 首次启动和依赖失效的就绪标准互相冲突

**依据**：[需求](../specs/mediavault-server/spec.md) AC-1、AC-10、FR-OPS-1；[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) 第 744 行；[发布阶段](../specs/mediavault-server/phases/08-hardening-release.md) T-801、验收 2。

AC-1 要求空库首次启动 `/readyz` 通过，但 readyz 同时要求 115 token 有效和已有 30D 同步记录；首次启动默认没有这两项，无法同时满足。AC-10 还要求 token 失效不影响其他功能，而若部署平台据 readyz 将实例摘流，本地浏览和管理配置也会不可访问。同步多久算过期、没有配置 115 是否算故障没有阈值。

**建议**：推荐 `/readyz` 表示进程能提供核心本地服务（迁移完成、DB 可用），外部依赖状态通过详细状态接口和告警报告；若坚持依赖全部健康才就绪，则修改首次启动流程与可用性承诺，并说明部署探针配置。

**验收**：首次空库、未绑定 115、token 失效、同步过期、DB 故障五种状态的 HTTP 状态和可用功能写成表并逐一验证。

## 5. 中优先级问题

### A18 — 关键路径和阶段依赖不一致，估算缺少验证前提

**依据**：[总计划](../specs/mediavault-server/plan.md) §1、§3、§5；[基础阶段](../specs/mediavault-server/phases/00-foundation.md) T-003；[后台阶段](../specs/mediavault-server/phases/07-admin-console.md) 前置依赖。

按总表计算，P3+P4 为 6～8 天，长于 P2 的 3～4 天；因此所列 `P0→P1→P2→P5→P6→P8` 不是该表的最长依赖链。图上 P7 只接 P4，但文字和阶段文件还要求 P5。单人总工作量相加为 **27～37 人日**；若资源足够、允许按依赖并行、忽略协调开销，则较长路线是 `P0→P1→P3→P4→P5→P7→P8`，约 **20～28 工作日**。二者不能混用。

P3 摄取需要评分和优选，但评分实现在依赖 P3 的 P4，需规定先以未评分状态交付再补算，或把纯评分能力前移。阶段 DoD 要求相关端到端 AC 可复现，但早期数据阶段无法独立完成客户端验收。依赖真实账号/客户端和协议探索的成本也未单列。

**建议及验收**：修正依赖图，增加验证门槛和可用测试资源前提，拆分阶段局部验收与最终 AC。重新估算时区分人日、日历排期、未知项和缓冲；不得把新增审核修订当作零成本。

### A19 — 性能与长期资源预算缺少可检验边界

**依据**：[需求](../specs/mediavault-server/spec.md) NFR-1～5；[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §3、§5.3、§9.1～§9.2；[发布阶段](../specs/mediavault-server/phases/08-hardening-release.md) T-809。

20～40MB 是空闲内存目标，不能替代同步、并发鉴权和图片处理时的峰值预算。`LIKE` 检索若使用前导通配符，现有索引不能保证毫秒响应；筛选排序、深分页和总数查询也没有数据分布、并发、硬件及 P95 条件。Go SQLite 驱动、CGO/静态链接方式尚未选定，镜像 <50MB 仍只是目标。

图片磁盘缓存没有容量/淘汰规则，下载包和运行记录也没有明确保留策略。以 21 万影片、每部缓存 100KB 图片作容量示例，图片就约 21GB，并非小到可忽略。在线搜索要共享低速上游，在六秒总时限内完成多次接口请求的成功率也未量化。

**建议及验收**：指定 SQLite 驱动、支持 OS/架构、单写者策略和构建方式；分别测冷/热查询、空闲/峰值内存、缓存磁盘增长、排队时间及服务端/端到端播放耗时。根据实测再确定组合索引、FTS 或搜索范围；给图片/下载/任务队列加预算和保留规则。压测本地替身服务，不依靠提高真实上游请求量验证容量。

### A20 — 部分需求没有对应任务或可操作入口

**依据**：[需求](../specs/mediavault-server/spec.md) US-5/8、FR-ADMIN-2；[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) §5.2、§10～§10.2；[刮削阶段](../specs/mediavault-server/phases/04-scraping.md)、[后台阶段](../specs/mediavault-server/phases/07-admin-console.md)、[发布阶段](../specs/mediavault-server/phases/08-hardening-release.md)。

下列承诺及其实施前提的任务或操作契约未闭合：用户指定时间的榜单定时抓取；磁力本身的手工修正；115 首次绑定和重新授权；多用户的创建/停用或至少 AC-9 的测试用户准备；媒体库配置入口；告警横幅的数据接口；配置修改立即生效对已有任务和 TTL 的具体影响。T-308 的 run 记录和转存 WS 进度还需与 A06 的状态存储统一。

**建议及验收**：增加 FR→设计→任务→验收的追踪表，给每项明确“本版实现/测试夹具/后续版本”。没有需求的功能不必新增，但已承诺的功能必须找到入口与验收，或正式调整范围。任务表增加状态列，才能执行 DoD 所要求的勾选完成。

### A21 — 六个媒体库混合影片分类与版本属性

**依据**：[主设计](./PROJECT_SPEC_GO_VIRTUAL_MEDIA_SERVER.md) 第 265～293 行、§7.4 第 565 行、§9；[需求](../specs/mediavault-server/spec.md) US-1/4。

一部影片只有一个 `category`，但“中文字幕”“4K”通常是资源版本属性，“FC2/国产/有码/无码”又是内容分类。一部有码影片同时有中字和 4K 版本时，当前单值列只能进入一个库；在线分类还优先看影片标题，而评分看磁力标题，可能出现有中字版本却不在中字库的情况。当前规则并非不能实现，但不能同时表达多维浏览。

**建议及验收**：明确六库是互斥主分类还是可重叠视图。推荐保留来源主分类，字幕/4K 通过资源谓词生成视图；若选择互斥分类，需列出冲突优先顺序和新增版本后是否重分类。验收同影片多个版本的库归属，同时保证全局搜索按影片去重。
